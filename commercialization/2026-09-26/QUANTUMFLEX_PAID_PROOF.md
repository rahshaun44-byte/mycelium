# QuantumFlex paid proof: one customer's Linux release, one independent challenge

**Decision memo, September 26, 2026.** This replaces the generic consulting-first recommendation in [REVENUE_EXPERIMENT.md](REVENUE_EXPERIMENT.md). The goal is a small payment for an actual QuantumFlex control that passes a buyer-observed test. Revenue is the market signal; the technical verdict is a separate signal.

## The commercial vector

**Offer:** a fixed-price, nonproduction **QuantumFlex Release Admission Challenge** for one customer-owned Linux executable. On a buyer-controlled host, a valid release must run through QuantumFlex's signed-manifest and launch gate. The buyer supplies or selects tampered release cases; they must be rejected. The buyer receives the commands, receipts, logs, pass/fail matrix, limitations, and rollback procedure.

**First buyer:** a small or mid-sized vendor that ships a standalone Linux service or appliance into customer premises or an edge site and owns its release process. A technical founder or engineering lead can authorize a small pilot. The strongest trigger is a release, customer security review, or contract renewal already scheduled in the next 60 days. A general PQC interest is weaker evidence of immediate demand.

**Acquisition with no warm contacts:** seek public high-intent work requests about signed software delivery, offline verification, Linux fleet updates, or cryptographic provenance; simultaneously contact vendors whose own documentation shows Linux/on-premise distribution. Qualify each buyer's existing toolchain. If Mender, RAUC, TUF, Sigstore, or kernel integrity controls already solve the exact need, ask what remains unsolved before proposing QuantumFlex. Do not assume a gap from a website.

**Price hypothesis:** $1,500 for a five-business-day nonproduction pilot, 50% paid to book and 50% due on accepted delivery. One binary, one Linux target, one customer-held test signing identity, six agreed challenge cases, and eight delivery hours are included. These terms are an experiment, not a market rate or a promised delivery date. Defer the start until the local readiness gate below passes and the customer provides access/artifact. Extra systems, production rollout, code audit, and key lifecycle work get separate scopes.

The long-run wealth path, if repeat buyers exist, is a repeatable Linux release control with onboarding, support, and evidence refresh sold to vendors deploying many instances. License structure and unit economics should be set from actual pilots. A first payment proves a narrow willingness to pay; three independent paid implementations with similar delivery hours would begin to show repeatability. It does not prove a large market or all QuantumFlex features.

The release-integrity problem has independent support: [CISA's software-supplier guidance](https://www.cisa.gov/sites/default/files/2024-08/SECURING_THE_SOFTWARE_SUPPLY_CHAIN_SUPPLIERS_508.pdf) recommends that suppliers let customers verify release integrity through digital signatures, and [NIST's Secure Software Development Framework](https://nvlpubs.nist.gov/nistpubs/specialpublications/nist.sp.800-218.pdf) includes retaining integrity and provenance information for releases. These recommendations do not prove that a specific vendor will buy this implementation.

The adjacent PQC demand context is real but does not itself prove a sale. [NIST's PQC migration FAQ](https://pages.nist.gov/nccoe-migration-post-quantum-cryptography/) says inventory and discovery are a starting point. [OMB M-26-15](https://www.whitehouse.gov/wp-content/uploads/2026/06/M-26-15-Execution-of-the-Migration-to-Post-Quantum-Cryptography.pdf) places federal inventory/planning in 2026–27 and encourages automation and provider engagement. [GSA](https://www.gsa.gov/technology/it-contract-vehicles-and-purchasing-programs/it-security/postquantum-cryptography) says it is requiring cryptographic visibility from vendors. These are reasons to ask federal-market suppliers about present needs. [EO 14412](https://www.whitehouse.gov/presidential-actions/2026/06/securing-the-nation-against-advanced-cryptographic-attacks/) directs a *proposed* future contractor rule; it does not create a current blanket CBOM certification requirement.

The market is competitive. ## Current engineering baseline and honesty boundary

The existing [runtime README](/home/quant/mycelium/quantumflex/README.md) describes an ML-KEM library package and A4 install receipt. The install receipt alone says `signed: false`; a separate A5 Ed25519 ceremony signs provenance. The current [migration notes](/home/quant/mycelium/docs/MLKEM_STRICT_MIGRATION.md) correctly state that `fips_strict` is a policy name, not FIPS 140-3 validation, and a KEM exchange is not proof that application traffic is PQ encrypted.

A read-only release inspection in this session reported a valid external Ed25519 signature and byte matches for 13/13 declared artifacts. The signing-ceremony script passed its focused assertions. These verify a narrow current release snapshot. They do not cover every running process, every dependency, the customer's release, or the full product.

**Readiness defect found and repaired in the repository during this review:** the A6 launcher expected a legacy `--admit-package --prefix` verifier interface while the installed host verifier accepts a manifest path and current options. Its prior 10-case suite stopped at Case 1. A separate invocation path could label an executable admitted without checking a signed A5 package manifest. The repository launcher now requires a current signed A5 manifest and verifies its artifacts before accepting the A6 runtime binding; its revised temporary-fixture matrix passed 11/11 cases, including an unsigned A5 manifest and executable path swap. The *installed* external launcher was not changed, and no customer host or artifact has been tested. Treat older “10/10” claims as historical. The repository launcher uses `/proc/self/fd/<fd>` to execute the opened binary rather than literally calling `fexecve`, and the hash covers the primary executable, not every dynamic library or interpreter.

The separate CMake A4/A5 installed-package flow still uses an older verifier contract and was outside this repair. The proposed pilot exercises the repaired signed-release A5/A6 path, not that installed-package flow. The root package license has been established under Apache License 2.0 with a NOTICE file recognizing third-party terms (nlohmann/json MIT).

The repository's `tools/qf_audit.py` uses regex matches in source text as findings, contains broad compliance language, and emits a CycloneDX 1.5 document while [CBOM support was upstreamed in CycloneDX 1.6](https://github.com/IBM/CBOM/blob/main/README.md). It must not be sold as a certified or comprehensive inventory. The release gate currently uses **Ed25519**, a classical signature. Do not call the signed release “post-quantum secure.”

## Independent test contract

The buyer observes the gate on their own nonproduction host or disposable VM. The exact chosen release, signing key ownership, supported Linux environment, and cases are recorded before test execution. A valid signed release must launch. At minimum the buyer selects cases from: one changed executable byte, altered manifest, removed signature, wrong signer, replaced package artifact, and binary path swap during the verify/execute interval. Unsupported or inconclusive cases are reported as such, never counted as passes. Record positive and negative exit codes, verifier reason, artifact hashes, signer identity, runtime version, OS, elapsed time, and manual interventions. The buyer keeps the evidence pack.

**Technical pass:** the current A5/A6 path passes its own fresh matrix; then the customer's legitimate artifact launches, all agreed invalid cases fail before executing the target, and the customer can repeat the commands without the seller. A false allow is a stop condition. A false deny or runtime compatibility problem requires a fix before acceptance. Successful cases establish only those cases, versions, and host conditions.

**Commercial pass:** a buyer unrelated to the team clears the deposit for this precise QuantumFlex challenge, supplies an artifact, witnesses/accepts the result, and requests either a second release, another host, or a rollout quote. Record deposit separately from final balance. One payment plus acceptance is a baseline, not product-market fit.

**Operational pass:** actual preparation, prospecting, engineering, delivery, support, and cash costs are logged. Contribution = cleared revenue − direct cash cost − delivery time valued at an explicitly chosen internal rate. Net profit also includes sales time, overhead, taxes, and fees. Do not infer high-margin software economics from a one-off pilot.

## Thirty-day test from a cold start

1. **Before selling a start date:** reproduce the repaired A6 test result; build a portable customer-style sample with an independent disposable signing key and a non-QuantumFlex ELF binary. Prove the positive case and the six rejection cases on a second Linux environment. Document trust-anchor installation and removal. Deploy the repaired launcher only after this check. If the gate cannot run on a separate executable without a rewrite, narrow the pilot or stop and revise the product.
2. **Days 1–7 after readiness:** identify 50 named, unique candidates with public evidence of Linux on-prem/edge delivery or a live signed-release request. Collect a buyer role and reason the timing matters. Search active work requests as well as direct vendor sites; prioritize disclosed problems over broad industry lists. Build one short demo clip or transcript from the actual reproducible sample. No fabricated customer result.
3. **Days 5–20:** submit tailored applications/proposals to relevant live requests and personalized direct outreach to the qualified list. A discovery call asks what they ship, where it runs, how they verify it today, their next release date, and who can authorize $1,500. Do not state that federal law currently requires this pilot.
4. **Days 15–30:** aim for three qualified discovery calls, two scoped proposals, and one cleared deposit. These are thresholds for learning, not forecasted conversion rates. Deliver one paid challenge only after technical readiness; record the buyer's independently selected cases and acceptance.

If 50 relevant contacts produce fewer than three discovery calls, revise the audience and message. If five qualified calls produce no deposit, revisit urgency and value before building more features. If a deposit clears but the technical acceptance test fails, suspend the offer and repair the control; do not count payment as product validation. If a first pilot succeeds, quote a second host/release and measure whether delivery time falls. Do not open a broad SaaS build until multiple buyers repeat that request.

**Cash baseline today:** $0 verified customer collections, 0 buyer pilots, and 0 contacted prospects in this session. The initial target is one independently cleared $750 deposit within 30 days of readiness. A zero result is useful evidence about the offer/channel, and should be reported plainly. Cold acquisition timing is uncertain.
